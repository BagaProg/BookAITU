# Административный API BookAITU

## Доступ и интерфейс

Первая роль администратора назначена явно подтверждённому аккаунту `260737@astanait.edu.kz` после проверки активного Microsoft-аккаунта и настроенной 2FA. Действие `user.bootstrap_admin` записано в журнал. Вход остаётся тем же: Microsoft → второй фактор. Отдельного пароля или обходного admin-login нет.

После перезапуска backend и обновления frontend в верхней панели появляется кнопка **Админ-панель**. Разделы: Обзор, Бронирования, Помещения, Пользователи, Журнал действий. Для возврата есть кнопка «Мои бронирования»; обычный пользователь кнопку не видит. Ограничение обязательно проверяется backend, независимо от видимости кнопки.

Все `/api/admin/*` требуют полной серверной сессии и актуальной роли `admin`. Роль/активность читаются из БД на каждом запросе. Ответы не кэшируются. POST/PATCH требуют `credentials: include`, точный Origin и `X-CSRF-Token`; тот же контракт сессий описан в [AUTH.md](AUTH.md). Анонимный запрос получает 401, обычный пользователь — 403. Административные изменения дополнительно требуют `PG_ALLOW_WRITE=true`.

## Обзор

**GET `/api/admin/dashboard`** возвращает `{metrics, upcoming, byStatus, timezone}` в согласованном read-only snapshot.

`metrics`: `today`, `users_total`, `users_active`, `admins_active`, `rooms_total`, `rooms_active`, `bookings_total`, `bookings_active`, `bookings_cancelled`, `bookings_today`. `bookings_active` — все записи без статуса cancelled за все даты, а не только будущие брони. Сегодняшняя дата определяется в `Asia/Qyzylorda`.

`upcoming` — семь дат начиная с сегодняшней, каждая `{date: "YYYY-MM-DD", count}` для броней без отмены. `byStatus` — `{status,count}` для статусов, фактически присутствующих в базе. Отсутствующий статус frontend может показывать как ноль.

## Списки, фильтры и пагинация

Общий ответ: `{items, total, page, limit}`. Идентификаторы BIGINT в `items` — строки. `page` начинается с 1, `limit` по умолчанию 25, максимум 100; `q` — до 100 символов. Пустая страница всё равно возвращает корректный `total`. Сортировка — id по убыванию, численно. Параметры запросов всегда передаются в SQL отдельно от текста запроса.

- **GET `/api/admin/users`**: фильтры `q` (имя/email), `active=true|false`, `role=user|admin`. Поля: id, email, name, role, is_active, two_factor_enabled, microsoft_linked, created_at, last_login_at. Парольные хеши, Microsoft ID, TOTP-секреты, recovery hashes и сессии не возвращаются.
- **GET `/api/admin/rooms`**: фильтры `q` (код/имя), `active`, `block=C1.1|C1.2|C1.3`. Возвращает и активные, и отключённые помещения.
- **GET `/api/admin/bookings`**: фильтры `q` (email/код/цель), `status=pending|confirmed|cancelled`, `room_id`, `from`, `to` в формате YYYY-MM-DD включительно. Возвращает пользователя, код помещения, период, цель, статус и сведения об отмене. Фильтр дат проверяет реальный календарь и порядок границ.
- **GET `/api/admin/audit`**: фильтр `q` (email администратора/action). Поля: id, actor_id, actor_email, action, resource_type, resource_id, before_data, after_data, created_at. Прямого API изменения или удаления журнала нет.

## Изменения

**PATCH `/api/admin/rooms/:id`** принимает любые из полей:

```json
{ "name": "Учебная аудитория", "capacity": 30, "is_active": true }
```

`name`: строка до 100 символов или null; пустая строка превращается в null, и UI отображает код. `capacity`: положительное целое или null (неизвестна). `is_active`: boolean. Блок, этаж, номер и код этим API не изменяются. Отключение блокирует новые брони, но сохраняет существующие. Удаления помещений нет.

**PATCH `/api/admin/users/:id`** принимает `role` и/или `is_active`:

```json
{ "role": "user", "is_active": false }
```

Администратором можно назначить только активного пользователя с Microsoft-привязкой и настроенной 2FA. Свой административный аккаунт нельзя отключить или понизить. Последний активный администратор сохраняется. Изменение роли или активности отзывает полные и незавершённые серверные сессии целевого пользователя; следующий вход требует Microsoft и второй фактор. Переключение статуса не удаляет пользователей и их брони. Изменять Microsoft ID, ключи 2FA или пароли этим API нельзя.

**POST `/api/admin/bookings/:id/cancel`**:

```json
{ "reason": "Помещение временно закрыто на обслуживание" }
```

Причина обязательна, 3–500 символов после обрезки пробелов. Запись сохраняется со статусом cancelled, временем `cancelled_at`, администратором `cancelled_by` и причиной `cancellation_reason`. Повторная отмена не перезаписывает первоначальную причину и не создаёт дубликат события.

Для совместимости `DELETE /api/bookings/:id` у администратора вызывает тот же сервис с причиной «Отмена администратором» и тоже записывается в журнал. У обычного пользователя этот маршрут работает только для собственных броней, сохраняет время/автора и причину «Отмена пользователем».

Некорректные поля/фильтры → 400, недостаточно прав → 403, объект отсутствует → 404, защищённое изменение роли → 409. Обновления с неизвестными полями отклоняются, а не молча игнорируются. Пустое PATCH-тело также отклоняется.

## Аудит и транзакции

Миграция `006_admin_panel.sql` добавляет три поля отмены и `admin_audit_log`. Перед её применением создан и проверен pg_dump backup. Существующие 11 пользователей, 261 помещение и бронирование сохранены; отдельно согласованному пользователю назначена роль admin.

Действия: `user.bootstrap_admin`, `user.update`, `room.update`, `booking.cancel`. До/после берутся из фиксированных безопасных наборов столбцов, поэтому секретов авторизации в журнале нет. Роль действующего администратора повторно проверяется внутри транзакции. Административные записи сериализуются advisory-lock; целевые объекты блокируются строковыми блокировками. Изменение объекта, отзыв сессий (если нужен) и аудит фиксируются одной транзакцией. Если аудит не сохранился, изменение откатывается. Запрос без фактического изменения не создаёт запись.

Скрипт `node src/bootstrapAdmin.js email@astanait.edu.kz` предназначен только для доверенного локального оператора с доступом к БД. Он назначает первую роль лишь при отсутствии активных администраторов, только подтверждённому аккаунту с 2FA, и пишет журнал. После первичной настройки роли меняются через административный API. Скрипт не является HTTP endpoint.

## Проверки

- `npm test`: 35 тестов, включая 10 тестов административного доступа, CSRF, валидации, аудита, транзакционного отката, защиты собственной/последней роли и отзыва сессий.
- `npm run admin:db:check`: реальные SQL и HTTP API против временных копий таблиц в транзакции. Проверены статистика, все списки, фильтры/пустые страницы, редактирование помещения, смена роли, отзыв сессий, отмена и журнал. В конце полный rollback; рабочие данные не меняются.
- Frontend: `npm run lint`, `npm run build`.

Все перечисленные проверки выполнены успешно. Текущий frontend — простой заменяемый интерфейс; другому разработчику достаточно этого контракта и [AUTH.md](AUTH.md).
